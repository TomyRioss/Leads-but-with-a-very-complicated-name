## Spec
Log actual del dev server al abrir /lead-suite (dos requests simultáneas del dashboard):
- `PocketBaseRequestError { status: 400, detail: '{"message":"Something went wrong while processing your request."}' }` → 502
- `PocketBaseRequestError { status: 404, detail: '{"message":"Missing collection context."}' }` → 502
La ruta llama en paralelo getLeadSuiteMetrics, listLeadContacts y getLatestWeeklyReport (lib/server/lead-suite.ts). El 404 indica una colección inexistente (probable `lead_suite_reports` si la migración se aplicó a medias); el 400 indica una consulta inválida para PocketBase.
Objetivo (SOLO leyendo código; prohibido ejecutar comandos de base, docker o requests directas a PocketBase):
1. Identificar qué consulta da 400. Revisá cada `pocketBaseFetch` del dashboard: formato de fechas en filtros (PocketBase espera `"YYYY-MM-DD HH:mm:ss.sssZ"` con espacio, no `T`; hay `toPbDate` en lib/lead-suite.ts: ¿se usa en todos los filtros?), operadores, campos inexistentes, `expand`/filtros por relación (`lead.batch.user`), `sort` por campos válidos, `perPage` > 1000, `skipTotal`, comillas/escape.
2. Corregí la causa del 400 en código.
3. Hacé que el log de PocketBaseRequestError incluya el path de la colección y la operación (sin el filtro con datos del usuario ni tokens) para que el próximo error diga exactamente qué colección/consulta falla. Si `lib/server/pocketbase.ts` es el lugar correcto para eso, agregá el path al error de forma mínima.
4. Degradación: si `lead_suite_reports` no existe (404), el dashboard debe seguir mostrando métricas y contactos y `latestReport: null` (catch específico de 404 en getLatestWeeklyReport), en vez de tirar 502 completo. Igual si falla solo el reporte.
5. En el cierre, decí qué colección da 404 según el código y el paso exacto que tiene que hacer el usuario.

Hecho cuando: 400 corregido con causa explicada, 404 del reporte no tumba el dashboard, logs con path.
