## Spec
Objetivo: backend del panel owner de Leadta. Login propio (separado de la sesión de usuarios) + API para administrar usuarios, créditos y membresías y ver métricas (MRR). La UI la hace otra tarea (ORQ-1-0003) contra este contrato: NO lo cambies sin avisar con `ask`.

Antes de codear: leé AGENTS.md y la guía de route handlers en `node_modules/next/dist/docs/` (esta versión de Next tiene cambios; `params` es Promise; mirá `app/api/auth/me/route.ts` y `app/api/subscriptions/[id]/route.ts` como patrón). Reutilizá `pocketBaseFetch`/`isPocketBaseConfigured` de `lib/server/pocketbase.ts` y el cliente MP de `lib/server/mercadopago.ts`. Patrón de cookie: `lib/server/auth.ts`. Sin dependencias nuevas (usá `node:crypto`).

### Auth owner
- Credenciales SOLO por entorno, nunca en código: `OWNER_EMAIL`, `OWNER_PASSWORD`, `OWNER_SESSION_SECRET`. Agregá las 3 (vacías) a `.env.example`. Creá/actualizá `.env.local` (está en .gitignore) con `OWNER_EMAIL` y `OWNER_PASSWORD` (valores que da el usuario; no se versionan) y un `OWNER_SESSION_SECRET` aleatorio de 48+ bytes hex generado con `node -e` (es un comando local sin DB; permitido).
- Cookie `leadta_owner`: httpOnly, sameSite lax, secure en producción, path `/`, 12 h. Valor = payload `{exp}` + HMAC-SHA256 con `OWNER_SESSION_SECRET`. Verificar con `timingSafeEqual`. Comparar email/password con `timingSafeEqual` (hash previo para igualar largos). Si faltan las env vars, el login responde 503 y nada autentica.
- Límite de intentos de login en memoria: 5 fallos por IP en 10 min → 429.
- `lib/server/owner.ts` exporta `requireOwner(request)` (devuelve `null` si OK o un `NextResponse` 401), `setOwnerCookie`, `clearOwnerCookie`, `verifyOwnerCredentials`. Todo `/api/owner/*` salvo `login` exige `requireOwner`.

### Contrato de API (JSON, mensajes de error en español como el resto de la app)
- `POST /api/owner/login` `{email,password}` → `{ok:true}` + cookie. `POST /api/owner/logout` → `{ok:true}`. `GET /api/owner/me` → `{owner:true}` o 401.
- `GET /api/owner/overview` → `{ mrrArs, activeSubscriptions, pausedSubscriptions, totalUsers, newUsers30d, creditsInCirculation, revenue30dArs, planBreakdown:[{planId,count,mrrArs}] }`. MRR = suma de `price_ars` de `subscriptions` con `status = "authorized"`. `revenue30dArs` = suma de `amount_ars` de `subscription_payments` aprobados (usá el status que escribe `app/api/mercadopago/webhook/route.ts`) creados en los últimos 30 días. Paginá las consultas a PocketBase con límite (perPage 200) y paralelizá las independientes.
- `GET /api/owner/users?page=1&perPage=25&q=` → `{ items:[{id,email,name,credits,created,subscription:{id,planId,status,priceArs,monthlyCredits}|null}], page, totalPages, totalItems }`. `q` filtra por email/name (escapá/validá el filtro de PocketBase, sin inyección). `perPage` máx 100. Resolvé las suscripciones de la página con UNA consulta (sin N+1). `subscription` = la más reciente con status `authorized`/`paused`/`pending`.
- `GET /api/owner/users/[id]` → `{ user, subscriptions:[...], payments:[{id,paymentId,status,amountArs,credits,created}] }`.
- `PATCH /api/owner/users/[id]` `{ credits?: number (absoluto, >=0, múltiplo de 0.5, máx 1_000_000), addCredits?: number (puede ser negativo; el resultado no puede quedar <0) }` → `{ credits }`. Exactamente uno de los dos. Usá el lock de `credit_locks` de `lib/server/credits.ts` para no pisar una búsqueda en curso (si necesitás exportar un helper nuevo desde ese archivo, avisá con `ask` antes).
- `POST /api/owner/users/[id]/subscription` `{ planId: "initial"|"pro"|"agency", grantCredits?: boolean }` → crea una suscripción manual en `subscriptions` (`external_reference` = `owner-<userId>-<timestamp>`, `status:"authorized"`, `price_ars`/`monthly_credits` desde `lib/plans.ts`, sin `mp_subscription_id`). Si el usuario ya tiene una `authorized`/`paused`/`pending`, 409. Con `grantCredits` suma `monthly_credits` a los créditos.
- `PATCH /api/owner/subscriptions/[id]` `{ status: "authorized"|"paused"|"cancelled" }` → `{status}`. Si tiene `mp_subscription_id` y hay `MP_ACCESS_TOKEN`, replicá el cambio en Mercado Pago igual que `app/api/subscriptions/[id]/route.ts` (reusá el cliente) antes de guardar local; si MP falla, 502 y no guardes. Sin `mp_subscription_id` (manual) solo local.
- Sin DELETE de usuarios. Sin migraciones ni cambios de schema: solo se usan colecciones existentes (`users`, `subscriptions`, `subscription_payments`).
